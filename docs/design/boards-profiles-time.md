# Job boards, profile avatars and site time

## Demo walkthrough

1. Sign in to the dashboard as `lead1@thbs.com` / `123456`. Open **Job boards → Create board**. Choose Fibre Delivery or Site Planning, enter the project name and optionally choose a client routed to that squad. The four existing delivery/review stages remain unchanged.
2. Open **Demo · Fibre rollout**. This synthetic board was created through the Team Lead UI and has a pending **Demo · Fibre rollout site visit** assigned to `fibre1@thbs.com`. Open its compact card to see the full instructions, assignment parties, response controls/history and site visits. Its current creator and assignee are shown separately. Revising an assignment records the latest assigning person.
3. Install the latest `Field-Assist-Android-Test.apk` (ARM64 Android 12+, build 2010). In sign-in **Connection settings**, use `http://192.168.1.4:3000` while the laptop and phone share reachable Wi-Fi and the laptop server is running. This is the current laptop address and can change when networks change. A different internet connection cannot reach the private laptop address.
4. App accounts all use `123456`: fibre1/fibre2@thbs.com, repair1/repair2@thbs.com, business1/business2@thbs.com and site-survey@thbs.com. Dashboard-only administrators, leads and Sales cannot sign in to the engineer app.
5. Accept the new visit in **My jobs**, then open its brief and choose **Check in** on arrival. Confirm a one-shot location fix and optional note. Use **Start break / Resume work**, then **Check out** when leaving (another one-shot location fix). These actions do not mark the report approved or automatically close the work order.
6. Open dashboard **Time tracking** as the engineer, responsible lead, administrator, Operations Manager or Viewer. Inspect arrival, departure, time on site, working time, break time and the action timeline. Each location shows accuracy, map link and a simulated-location label when reported. Sales does not receive personal timesheet access.
7. Choose avatars on the website through **Account settings → Choose profile avatar**, or in the app through **Your settings → Your profile avatar**. There are **133 avatars across eight styles**, plus initials. Style filters, a persistent preview and an explicit Save button make the full catalogue browsable. The existing theme colours and mobile Light/Dark/System setting remain.

## Behaviour and boundaries

- Dashboard cards are compact, approximately 246 × 165 px at the tested desktop breakpoint. A card is one keyboard-accessible button; click/Enter opens a modal with full details. Engineer views arrange their own cards in a responsive grid. Small layouts stack stages.
- Leads can create boards only for squads they lead; engineers can read only boards containing their own assigned jobs. Sales boards require a routed client. Board assignment checks squad and client compatibility independently on the server. Existing jobs without a board remain available. The board list explicitly caps its latest permitted results at 200.
- Avatars are catalogue IDs, never arbitrary remote URLs or uploaded files. All PNGs and the MIT notice are bundled in both apps. Selected avatars appear on assignments, profile views and organisation people cards. Existing selected IDs remain valid. Profile updates require connectivity; saved images display offline.
- The pinned source is [Alohe avatars](https://github.com/alohe/avatars), commit `a2ab6d008876133ac16a5484bf29aef22d42e4a0`. Catalogue styles: Vibrant (27), 3D (5), Blue portraits (10), Soft 3D (35), Line art (15), Team portraits (9), Cartoon (10), Sketches (22). Images total 1,036,678 bytes per app. Licences are retained in each asset directory and exposed from the profile/settings UI.
- Site tracking is deliberate check-in/out, not geofenced arrival detection. It does not continuously collect background location. Action timestamps come from the phone; separate server receipt timestamps remain visible. The server rejects backwards action times, sequence gaps, missing arrival/departure fixes, stale fixes, timestamps more than five minutes ahead or older than 31 days, and invalid break transitions. Location accuracy and mock flags are evidence, not proof that a person physically reached the named site.
- There can be one active visit per engineer. Job reassignment/editing is blocked while a site visit is open. Multiple completed visits are retained. Elapsed time is calculated from saved timestamps and continues across screen closure, app restart and temporary disconnection; working time excludes recorded breaks.
- Mobile time actions use the existing per-account SQLCipher outbox. Stable request IDs and immutable database events make retrying a lost HTTP response safe. Queued assignment acceptance is delivered before check-in; time actions retain insertion order. The server enforces sequence and state atomically. A queued label means saved on the phone, not acknowledged by the server. Blocked time actions are visible in Messages → Outbox with Retry, and later dependent actions wait. Time actions cannot be discarded out of sequence; there is no timesheet correction UI in this version.
- Latest 100 downloaded time visits plus an active visit are cached for mobile, with the latest 10 for a job expanded in its brief. The dashboard paginates 50 visits and job details show 10 with a link to the full timesheet. Previously downloaded history remains encrypted on that account's device. Dashboard records appear after synchronization.
- Engineer timesheets are owner-only. Leads see the visit's original squad, preserving the time record's scope if a person later moves teams. Cross-organisation IDs and user/job filters cannot widen access. Private messaging rules are unchanged. Phone alerts still require the app to be open/unlocked; no FCM/APNs closed-app push provider is configured.

## Verification

- 111 Flutter tests, including duration/restart calculations, queued-to-received deduplication, blocked action restoration, both theme layouts on a narrow phone, and a database-bound enqueue regression for account changes. Flutter analysis is clean.
- 84 shared contract tests; 54 workspace HTTP/PostgreSQL checks; 97 collaboration and 93 account regression checks. Tests use isolated synthetic organisations, then disable users and revoke sessions while preserving immutable history.
- Native iPhone simulator proof reopens the actual SQLCipher database, simulates unreachable transport and a lost check-in response after server commit, then delivers one visit with four actions. Assertions verify 540 seconds on site, 420 working and 120 on break, acceptance-before-check-in, cached final state, avatar save and encrypted file header. Locations were synthetic/mock data. This does not certify physical Android permissions, hardware GPS, OS airplane mode, background execution or a real 16 KiB Android device.
- Browser checks cover compact-card dimensions and detail modal, all 133 avatar images loading, style filters, Team Lead creation restricted to its two squads, client/board-prefilled assignment to the correct squad engineers, and the resulting pending card. No real employee messages were sent.
- TypeScript and the production dashboard build pass. Final iOS/Android build and APK verification evidence is retained under `docs/evidence/workspace-*`. The normal simulator app is restored using the public configuration after native tests. Private fixture credentials are excluded from the downloadable APK.
