# Guided voice and demo rehearsal — 15 October 2026

Voice opens as a full-screen conversation. The assistant speaks the first missing, relevant voice-enabled question before requesting microphone access or listening. For the fibre installation outcome it asks whether the work is fully completed, partially completed or not completed. The same three choices can be tapped. Other templates use their configured questions and options; the client does not add fields to signed forms.

For a form with missing mapped cable-label fields, voice entry now starts with a spoken cable introduction and **Scan label**, **Enter details**, and **Not available**. This introduction does not open the microphone. Scanning uses the existing local camera/OCR and editable review; Apply must commit to encrypted storage before the summary reports saved details. Cancelling or denying a scan leaves the alternatives available. Enter details lists only missing/invalid mapped fields; the engineer selects which to provide. The assistant reads only those prompts, and the engineer types/reviews each printed value before Save & next. This preserves the published template's camera/touch policy for label identifiers. Each accepted detail saves locally; a failed write stays on that question for retry. Continue to work questions starts the existing voice conversation. Not available leaves label values blank and goes directly to the work questions.

Cable identification has a separate optional progress count; the main progress bar describes required fields. Printed cable length never replaces the amount actually installed, and reviewed scan/manual sources remain distinct from spoken work answers.

The original indigo/teal colors and Light/Dark/System preferences are retained. The lower glow moves while listening or speaking, with intensity from actual microphone/playback levels. Processing, paused, Reduce Motion and constrained-power states use a static glow. Pause/Resume, End and Done speaking have normal button semantics and shared press feedback. The last saved answer is labeled with its field name, distinct from the next question.

## Answer handling

1. The bot finishes playback, waits a short echo tail, then listens. On Android one shared audio session owns focus throughout the conversation; the recorder does not request a second focus owner. Soft notification ducking briefly lowers question playback while capture continues. Calls, non-mixable OS focus loss and headset route safety still pause through the shared session. No phone-state permission is added. Current source measures 20 ms microphone PCM RMS frames and ends the turn after 1,300 ms of silence for numeric/choice answers or 1,500 ms for dictation; Done speaking remains an optional fallback. Speech needs a continuous 180 ms burst, and the RMS threshold stays at .004 rather than increasing after a loud word. Full captured audio reaches recognition without energy trimming. Recorder echo cancellation and noise suppression are disabled, restoring the pre-2014 configuration. An empty turn times out at eight seconds, and capture has a twenty-second maximum. This accuracy repair is not yet packaged: the installed APK remains build 2014 with its earlier 650/900 ms windows and trimmed input.
2. Whistle transcribes on device. Exact options, direct text dictation and explicit numeric answers are handled conservatively; other answers use Needle extraction focused on the active question. Completion requires an explicit recognized choice, including natural negative phrases such as “I have not completed the work”; unrelated words such as “excellent” prompt clarification without model guessing or saving a completion status. “Twelve metres” and “minus twenty two point four” retain their typed quantity and signed reading. Normal type, constraint, ambiguity, negation and merge validation still apply. Existing values require an explicit correction to replace them.
3. Each validated patch commits to encrypted SQLCipher storage before the assistant says Saved or asks the next question. The screen shows the saved field and its value. Touch and voice provenance remain distinct. A failed write displays an unsaved error and retry action; it does not acknowledge success. End finishes captured or in-flight speech and waits for the write before returning to the form. If that write fails, Retry or explicit discard remain available. Pause interrupts the current turn.
4. Required relevant questions come first, followed by remaining voice-enabled optional questions. Optional questions offer Skip; hidden conditional questions are not asked. Missing/uncertain answers receive bounded clarification, then touch entry remains available. Voice-disabled fields, such as an ONT serial on a completed installation, are named in the final handoff and must be entered by touch/scan. The bot cannot invent them or submit a report.
5. Returning from voice reloads the encrypted report into the actual form controls and refreshes the Reports/Home list. The save counter describes completed voice-enabled fields, not an upload or server receipt.
6. Qualifiers such as “around thirty metres” create a typed **30 m** proposal instead of silently dropping the answer or recording an estimate as confirmed. The bot asks whether to record it; spoken Yes or Use 30 m commits it through the normal validated save path. No/Answer again discards the proposal and repeats the active question. Unsupported units, alternatives and invalid ranges are not accepted as proposals. Ending before confirmation does not save the proposal.

## Optical question and response time

In the current published fibre form, ONT serial and optical reading are visible/required only when installation outcome is Completed. Partial and Unable skip both; they require an exception reason instead. Optical is voice-enabled and accepts “minus twenty two point four dBm” as -22.4, while ONT serial stays typed entry. For the synthetic completed rehearsal, use the extended scan card as a reference; only its eight cable rows are mapped by the scanner.

The user confirmed build 2013 listens and saves on the physical realme, but reported a long wait. Build 2014 introduced shorter silence windows, recorder speech effects and audio trimming. The user initially confirmed quicker automatic saving, then reported “not completed” becoming “bots”, “excellent” or “excited”. Controlled regressions reproduced quiet audio being removed and answers ending during a natural pause; these checks do not identify every cause in live phone audio. Current source restores the full audio and earlier recorder configuration, allows a longer natural pause and prevents unrelated completion transcripts being guessed. A separate short Saved acknowledgment still plays only after encrypted persistence, before synthesis of the next question. Its RAM cache remains bounded to 12 prompts/8 MiB. Capture, recognition, validation and save use the same local path online and offline; no cloud fallback is introduced. Recognition remains utterance-based rather than word-by-word streaming. The repair awaits the next explicitly requested APK and physical microphone retest.

## Offline delivery

Draft answers save locally even without internet after successful initial sign-in, provisioning and local unlock. Review and explicit Confirm are still required. Confirm freezes the validated report and atomically queues it in the encrypted outbox; draft answers are not uploaded.

The unlocked app now checks queued work every five seconds and retries after failures with backoff up to sixty seconds. Report-specific retry deadlines are retained. Unlock also attempts delivery. The same report ID, frozen bytes and payload hash are retried, and an already accepted attempt returns the existing server receipt. Saved, queued and accepted are different states.

This is foreground delivery: there is no promise that an OS-killed or suspended application will upload in the background. Reopen and unlock to resume. Internet access alone is insufficient if the configured API is unreachable. The current manual APK still targets the laptop loopback API, so a standalone phone needs a reachable backend configuration for initial sign-in/provisioning and delivery. No hosted backend has been deployed.

Before presenting, sign in/provision online, verify local voice readiness, enable Settings → Spoken questions, check media volume, and approve microphone access yourself when prompted. Choose Light or Dark. Use a fresh fibre report to show the completion question; an existing draft resumes its missing fields.

If the published template includes additional required fields, answer those too. Inspect each Saved acknowledgment. Use Done speaking if room noise prevents the silence endpoint; touch options or End → form remain available. Review every value before Confirm.

For the offline segment, disconnect backend access, answer a question, End, and reopen the draft to show recovery. Complete and confirm it while disconnected, show Queued, then restore actual backend reachability and keep the app open/unlocked. Allow the current retry backoff, or use Sync. Refresh the dashboard if needed and show the server receipt. A simulator airplane-mode icon alone is not evidence of lost host-network access.
