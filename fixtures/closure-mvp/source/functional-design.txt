FTTP engineer closure assistant 

Comprehensive MVP functional design, conditional questionnaires, five business cases and validation plan 

Version 1.0 • 21 October 2026 • Design hypotheses, not internal Openreach policies 

1. Executive scope and evidence boundaries 

Build one AI-assisted closure capability embedded in the field-engineer job journey. It converts engineer voice/text into candidate structured answers, activates only applicable questions, requests missing mandatory facts, and prepares a human-approved close / partial / referral outcome. There are five scenario-specific banks of 25 synthetic questions (125 total); an engineer will normally see only a conditional subset. These are not copies of Openreach production forms. 

Official Openreach public guidance documents the drop route, external junction, ONT, tests, customer permission and possible civils delays. Reddit discussions illustrate plausible field exceptions but are anecdotes. The number “20–25 questions” is reported in this project’s stakeholder conversation and remains to be validated against actual forms and policy owners. 

2. Scenarios and stage-sensitive definition of done 

S1 — Standard FTTP provision 

Starting context: Existing CBT and usable route; test passes 

Closure gate: Close completed install only if optical and operational evidence pass 

Openreach / BT business case: Faster accurate closure; improved job throughput and partner/customer experience 

Leading KPIs: Closure time, corrections, revisit rate. Primary monetisable driver: Closure minutes avoided per completed job. 

S2 — Blocked underground duct 

Starting context: Existing route blocked before fibre can be completed 

Closure gate: Close visit as blocked/partial; create civils dependency, never service-live 

Openreach / BT business case: Reduce repeat truck rolls and handoff latency; preserve truthful order status 

Leading KPIs: Repeat visits, re-triage, time to civils acceptance. Primary monetisable driver: Avoided repeat visits and triage minutes. 

S3 — Missing or incorrect CBT 

Starting context: Serving terminal missing, wrong, inaccessible or network records disagree 

Closure gate: Record asset discrepancy; route to network data/build owner; no live closure 

Openreach / BT business case: Higher data quality; fewer futile appointments and better build-to-provision handoffs 

Leading KPIs: Wrong-team reassignment, preventable visits, record correction time. Primary monetisable driver: Avoided wrong-asset revisits. 

S4 — ONT fitted, service not active 

Starting context: Indoor installation complete but external fibre, optical signal or activation fails 

Closure gate: Partial install or technical exception; distinguish no-light from provider activation 

Openreach / BT business case: Prevent premature completion, unnecessary customer contact and repeat diagnosis 

Leading KPIs: False-complete frequency, complaints, repeat diagnostics. Primary monetisable driver: Avoided false completions and follow-up hours. 

S5 — Remote property multi-stage build 

Starting context: No usable nearby fibre; survey, consents, civil works, cable/splice, readiness and final install may be separate work orders 

Closure gate: Close each stage against its own acceptance criteria; customer service not live until final provision 

Openreach / BT business case: Reduce queue latency, rework and handoff leakage across teams; enable accurate stage readiness 

Leading KPIs: Handoff delay, missed dependencies, rejected as-builts, completion-to-ready lag. Primary monetisable driver: Reduced inter-stage delay and rebuild/rework. 

3. Conditional question engine 

Each question has a stable ID, data type, expression/trigger, source, evidence requirement, validation rule and review status. Re-evaluate visibility and requiredness whenever any upstream answer changes. Hidden fields are not counted as missing and must not be silently reused for another branch. Keep an audit trail of changes and branch transitions. 

Minimum state model: NOT_SHOWN → ACTIVE_UNANSWERED → ANSWERED_UNVERIFIED → VERIFIED; branch changes may mark a previous answer NOT_APPLICABLE while retaining its history. Safety or permission holds supersede nominal pass responses. Do not mark the customer service live because an ONT is present or because an upstream network-build work order passed.

5. Deterministic branching and safety overrides 

B01 [all] IF Q05=yes THEN OPEN safety evidence + escalation; HOLD if unmitigated hazard. Control: Never auto-close on unmitigated safety issue 

B02 [all] IF Q06=no THEN OPEN permission/refusal reason; avoid installation tasks. Control: Do not infer permission 

B03 [all] IF Q08=yes THEN REQUIRE next owner + task reference + status. Control: No orphan partial job 

B04 [S1] IF drop route=underground AND obstructed THEN TRANSFER to S2 blocked-duct logic. Control: S1 cannot complete 

B05 [S1] IF optical test=pass AND service live=yes AND evidence present AND safe THEN ALLOW completed provision. Control: Human confirms final action 

B06 [S2] IF obstruction cannot be cleared safely THEN REQUIRE civils reason, section, follow-on ticket. Control: Blocked is not completed provision 

B07 [S2] IF civils needed=no AND route later clears THEN RESUME install/optical sequence. Control: Re-evaluate rather than stale branch 

B08 [S3] IF CBT missing OR mapping mismatch THEN REQUIRE asset mismatch evidence and data/build referral. Control: No fabricated CBT ID 

B09 [S3] IF alternative CBT suggested THEN REQUIRE explicit authorization before use. Control: No unauthorized asset choice 

B10 [S4] IF ONT=yes AND fibre connected=no THEN SKIP optical activation claims; PARTIAL status. Control: ONT presence ≠ service live 

B11 [S4] IF optical pass AND activation fails THEN OPEN provider/provisioning issue; preserve optical readings. Control: Distinct root cause 

B12 [S5] IF wayleave required=yes AND granted=no THEN BLOCK construction segment dependent on wayleave. Control: No unauthorized build 

B13 [S5] IF civils stage completed THEN REQUIRE reinstatement / as-built before handoff. Control: Stage closure only 

B14 [S5] IF all network stages accepted AND premises ready THEN ALLOW readiness handoff to final install. Control: Network ready ≠ customer live 

B15 [all] IF speech missing a required triggered fact THEN ASK concise missing-only follow-up; never guess. Control: Low hallucination risk 

6. AI extraction and interaction contract 

The AI returns candidate answers with: questionId, value, sourceSpan, sourceType (speech/job pack/test/evidence), confidence, evidenceId, verificationStatus, and ambiguityReason. Engineer corrections are authoritative subject to policy validation. The rules engine determines the next question; LLM output does not decide policy and cannot bypass the safety gates. 

Example: “ONT is in, but the underground duct is blocked after the second chamber. No light. I have raised a civils request.” Extract ONT fitted=yes; route=underground; obstruction=yes; service live=no; civils requested=yes. Ask only missing relevant items: second chamber asset ID, civils ticket reference, safe site state and customer notification. Do not assume a test was successfully run.

The companion workbook includes editable annual job volume, minutes saved, avoided visits per 1,000 jobs, cost assumptions and year-one integration cost. Scenario-specific sample values are illustrative, not BT/Openreach forecasts.

8. MVP app integration architecture 

Job-context adapter: job type / identity / stage → context. Never fill from assumption 

Speech/text layer: engineer narrative → transcript. Offline capability subject to device benchmark 

Extraction engine: transcript + context → candidate fields. Evidence and confidence per field 

Rules engine: question configuration + candidate answers → active subset. Deterministic, versioned, testable 

Evidence verifier: photos + tester output + permission → validation state. No fabricated test results 

Engineer review: candidate fields + prompts → approved payload. Mandatory human confirm 

Job-closure integration: approved payload → draft/submit. Audited API and idempotency 

Strategic integration: the supplied February 2026 App Strategy Review page 19 places allocation, execution, testing, completion and closure under OneApp/MyServices; pages 22 and 68 discuss ARENA evidence, quality and AI-assisted capture. Treat these as planned target architectures to validate with current application owners.

10. Engineering delivery and exit criteria 

Day 1: confirm five test journey definitions, canonical events and sample mocked job packs; jointly approve proposed question banks. 

Day 2: implement deterministic visibility/requiredness rules and unit tests, including changed answers. 

Day 3: implement speech/text extraction with synthetic transcripts; attach provenance to every parsed field. 

Day 4: build demo form renderer, field validation, evidence placeholders and missing-only clarification UX. 

Day 5: add stage disposition decision, human review, audit and integration stub (no production mutation). 

Day 6: run 20 included decision-path tests plus negative, offline and safety tests; instrument business KPIs. 

Day 7: stakeholder walkthrough, metric baseline agreement, defects and decision on controlled pilot. 

MVP done when: all 125 bank entries are uniquely versioned; 20 pathway tests pass; all triggered mandatory questions are resolved or hold is explicit; all five unsafe/false-complete branches refuse completion; edits re-evaluate branches; each candidate answer has source trace; outputs are approved by a human; no auto-commit occurs; latency and completeness are measured.
